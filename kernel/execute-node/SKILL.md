---
name: execute-node
description: Takes one planned piece of work — goal, files allowed to change, the mechanism the plan already chose, one verification command — and delivers the smallest change plus a report. Use before touching any file: first read the code from entry to exit and search out every caller, then change along the chosen mechanism, then run only the given verification. Return here when verification fails and a retry is tempting: the retry must change a different link in the chain, and two failures of the same verification stop the work. Return here too when the chosen mechanism does not fit the code as read: write the evidence down with paths and line numbers and hand it back — never pick a new mechanism oneself.
---

# 照计划执行（execute-node）
用于：手上有计划里派下来的一块活（一个节点：要达成的目标、它服务的那条完成条件、允许改的文件、计划已经挑好的做法——复用代码库里哪一处现成的东西，或者"新写：<什么>"、一条验证命令、划在外面这次不做的事、时限），要产出改动、验证的输出和一份报告的时候。做法是计划挑的，这里照着做；打开代码一读发现这个做法走不通，就把读到的东西写下来交回去，由派活的人重新挑。

何时：领到一块活之后、第一次动手之前；验证没过、想再试一次时，也回到这里。

走法：

1. 打开允许改的每一个文件，顺着代码从入口到出口实际怎么走看一遍，再写下这块活要让什么成真、它服务的是哪一条完成条件
   怎么做：
     a. 找入口：在这块活的目标里挑出那个会被外面碰到的名字（一个函数名、一条路由、一条命令、界面上的一个按钮），在允许改的文件里搜它，打开命中的那一处。做到：你写下了一个「路径:行号」，那一行是外面的东西第一次进入这段代码的地方。
     b. 走到出口：从入口那一行往下读，每遇到一次调用就打开被调用的那个文件接着读，一环一环记成 `路径:行号 → 名字 → 路径:行号`。做到：链条的最后一环是结果离开这段代码的地方——返回给调用者、写进文件或者数据库、打印出来、发出一次请求，四种里的一种。
     c. 列调用者：把这次准备改的每一个函数的名字，逐个放进 `grep -rn "<名字>" <仓库根目录>` 跑一遍，命令原文和它打出来的每一行都留着。做到：每一条命中都写成一行「路径:行号 — 这次改动会经过它／不会经过它，因为 ___」，两种写法各自填的理由不一样。
     d. 写下这块活要让什么成真：一句话，说现实里会看到什么和现在不一样。做到：这句话里出现了 b 那条链条上的至少一环。
     e. 抄完成条件：从这块活给的东西里，把它服务的那条完成条件抄成原文的精确子串。做到：抄下来的字符串能在原文里一字不差地找到。
     f. 做不到时：某个文件打不开，就写下它的路径和报错原文，把这个文件从这次改动里划出去，其余几步照做。
   → 留下 `node_goal`：一句话，现实里会变成什么样；`done_when_ref`：那条完成条件的原文片段（原文的精确子串）；`flow_trace`：从入口到出口的那条链条，每一环带路径和行号；`callers`：跑过的搜索命令原文，加上每一条命中「这次改动会不会经过它」的那一行。
   填不出："这个文件读不到：<路径> ＋ <报错原文>"。
   写进报告的哪一栏：summary。

2. 按计划挑好的那个做法，做让这块活的目标整体成真的改动——行数最少的那一种做法，而不是只交一半
   怎么做：
     a. 抄做法：从这块活给的东西里，把计划挑好的做法抄成原文的精确子串。抄下来的是复用代码库里某一处现成的东西，就打开那个路径读一遍，写下它现在收什么、给出什么；抄下来的是"新写：<什么>"，就写下要新写的那个东西的名字和它要落进哪个文件。做到：你手上有一行「这次用的是 <路径 ＋ 函数或者类的名字>」，或者一行「这次新写 <名字>，落在 <路径>」。
     b. 先列行：动手前把准备加或者改的每一行写成一句「这一行让 `node_goal` 的哪一段成真」。做到：每一行都对上了 `node_goal` 里的一小段；对不上的那几行还没进文件就先划掉。
     c. 逐行做减法：改完之后一行一行问「把这一行删掉，`node_goal` 还成不成立」。还成立的删掉它，再跑一遍第 3 步的验证。做到：剩下的每一行，删掉都会让目标不成立，或者让验证的输出变样。
     d. 共用的函数改一处：拿出 `callers` 那份清单，坏的要是这些调用者共用的那个函数，就在那个函数里改一次，让清单上的每一条一起被覆盖。做到：清单上每一条要么被这一次改动经过，要么旁边有一句它为什么用不上这次改动。
     e. 该保留的照样写全：外面的数据第一次进来的那一行照样校验；出错时会丢掉已有数据的地方照样把错误接住；这块活点名要的每一样能力都做出来。做到：这三样各写出一个「在哪个文件哪一行做了」；这次确实没有的那一类写"此类无"，并写一句为什么这次没有。
     f. 有判断的地方留一个能跑的检查：挑最小的那一个——逻辑坏掉它就失败，不靠框架，也不靠预先准备好的数据。做到：这个检查用一条命令跑得起来，而且你跑过一次，看到它通过。一行就能读懂的改动搁下这一条。
     g. 故意的简化写清楚：为了先跑通而留下的粗做法（整体加一把锁、随数据量平方变慢的写法、粗糙的猜测规则），在那一行旁边加一条以 `ponytail:` 开头的注释（代码里一行普通注释，用这个词开头，以后一搜就找得到），写成 `ponytail: <多大规模、什么输入下会失效>；以后换成 <什么>`。做到：这条注释两个空都填了，读的人不用问你就知道什么时候得换掉它。
     h. 范围外看见的活：写成一行进 `remaining`，说清在哪个文件、是什么活、这次为什么搁着，然后接着做手上这块。做到：这一行里有一个能打开的路径，还有一句说的是那件活本身。
     i. 计划挑的做法在代码里走不通时：把读到的东西原样写下来——那处现成的代码在哪个路径的哪一行、它实际收什么给什么、和 `node_goal` 的哪一段对不上（或者要新写的东西落不进允许改的文件，是哪个文件挡住的），然后停在这里，`status` 取 blocked，把「这个做法走不通」和读到的证据一起写进 `remaining` 交回去，接着换哪一种做法由派活的人挑。做到：写下来的每一句都带路径和行号，而且 `remaining` 里那一行说的是发现了什么，不是一个新的做法。
     j. 做不到时：不碰允许之外的文件就没法让目标成真，就把目标里成不了真的那一部分连同挡住它的文件路径写进 `remaining`，`files_changed` 只留真正改过的那几个。
   → 留下 `files_changed`：真正改过的文件路径，每一项都在允许改的文件之内；改动里只含让目标成真所需的行，用的是 a 抄下来的那个做法。为了先跑通而故意留下的简化（整体加一把锁、随数据量平方变慢的写法、粗糙的猜测规则），在那一行旁边写明它在多大规模、什么输入下会失效，以及以后怎么换掉。
   看见允许改的范围之外还有活，一行写进 `remaining`，写进报告交回给派活的人。
   填不出："一个字没改，因为…"（`files_changed` 为空，只表示在允许改的文件里没有改动）；计划挑的做法走不通时写"计划挑的做法在代码里走不通：<路径:行号> ＋ <读到的实际情况>"，`status` 取 blocked。
   写进报告的哪一栏：files；走不通那一种同时进 status 和 remaining。

3. 只跑这块活给的那一条验证命令
   怎么做：
     a. 抄命令：从这块活给的东西里把那条命令一字不改地抄下来。做到：抄下来的字符串和原文逐字相同。
     b. 定目录：写下要在哪个目录下跑它，用绝对路径。做到：这个路径就是你在终端里 `pwd` 打出来的那一行。
     c. 跑一次，等它自己结束，把命令原文、退出码、stdout、stderr 四样原样贴上。做到：贴上去的文字和终端里的文字逐字相同；输出长就整段留着。
     d. 读一遍输出，写一句它说明了什么：过了还是没过，凭输出里的哪一句话或者哪一个数字。做到：这句话里引了输出中的一个片段，片段能在贴上来的输出里原样找到。
     e. 验证是一次查看、不是一条跑得起来的命令时：把当时看到的实际状态原样贴上——打开的文件路径加上那几行原文，或者界面上那句话的原文，或者接口返回的那段原样内容；再写一句它和验证要求的哪一部分对上了。做到：贴上来的每一段都能在它原来待的地方一字不差地找到。
     f. 做不到时：命令跑不起来，就把命令原文和报错原文一起贴上，写成"跑不起来，因为…"。
   → 留下 `verify_output`：命令、退出码、stdout、stderr，四样原样贴上。
   填不出："跑不起来，因为…"。
   不适用："这块活给的验证是<原话>，它不是一条能跑的命令"，改成把当时看到的实际状态原样贴上。
   写进报告的哪一栏：evidence。

4. 验证没过就在计划挑好的那个做法之内换一处再跑一次；同一条验证命令连着失败两次就停下
   怎么做：
     a. 先找从哪一环开始不对：从 `verify_output` 里挑出报错的那一行、或者和预期对不上的那一行，回到 `flow_trace`，指出它对应链条上的哪一环。做到：你写得出一句「结果从 <这一环> 开始和预期不一样」。
     b. 分清"换一处"和"再试一次"：同一段代码再跑一遍、只改一个数字、只调换顺序、多加一句打印，这些都算再试一次；换一处是指改动落在 `flow_trace` 的另一环上，用的还是计划挑好的那个做法。做到：你写下「这一次改的是 ___，上一次改的是 ___」，两个空填的东西不一样，而且两次都在第 2 步 a 抄下来的那个做法之内。过不去的正是那个做法本身，就照第 2 步 i 停下，`status` 取 blocked。
     c. 第二次还是没过就停：把两次的输出都原样附上，每一次配一句它换了哪一处。做到：报告里有两段原始输出，两段之间那句话说的是这两次改在了链条上的哪两环。
     d. 定 `status`：先写一句「接着要做的下一件事是 ___」；这件事你自己能接着做，取 failed；要用户先定一句话才能做——改不改目标、花不花钱、动不动生产、缺一份你手上没有的授权——取 blocked；计划挑的做法走不通、要重新挑一个，也取 blocked；目标成真而且验证过了，取 completed。做到：三个值里只写了一个，那句「下一件事」也写出来了。
     e. 写失败或者卡住的报告，三样写全：停在哪一步（把那一步的原话抄上）、两次的原始输出、每一次试了什么。做到：读的人照着这三样就能自己把你跑过的东西重跑一遍，中间用不着回来问你。
     f. 收 `remaining`：把没做完的活和第 2 步 h 记下的范围外的活并成一份清单，一件一行；两样都没有就写"无"。做到：清单里每一行都有一个能打开的路径，或者一件能马上开始做的事。
     g. 做不到时：第二次连跑都没跑起来，就把原因原文写上，`status` 取 failed 或者 blocked，其余几栏照 c 到 f 填。
   → 留下 `wrapup`：`status` 取 completed、failed、blocked 之一（卡在只有用户能定的事上、或者计划挑的做法要重新挑，取 blocked）；没过时把两次跑出来的输出原样附上，并写清每一次换的是链条上的哪一环；`remaining` ＝ 没做完的活，加上允许改的范围之外看见的活，都没有就写"无"。
   填不出："第二次连跑都没跑起来：<原因原文>"——这一句就够写进报告，`status` 取 failed 或者 blocked。
   写进报告的哪一栏：status、evidence、remaining。

做到了：四步留下的东西都齐了；`files_changed` 每一项都在允许改的文件之内，用的是计划挑好的那个做法；`callers` 每一条都写了这次改动经不经过它；`verify_output` 是那一条验证命令的原样输出。

为什么：做法是在派活之前定好的，手上这一步只负责让它在真实代码里成真——多做的每一行都是别人的活。

每一步来自哪个方法：
- 第 1 步 ← 先懂再改（trace the real flow end to end）＋ bug 报告说的是症状（a bug report names a symptom）：改错地方的最小改动是第二个 bug，所以先从入口走到出口，再把准备改的函数的调用者全搜出来。
- 第 2 步 ← 整体交付不做半版（implement whole, not MVP）＋ 最短能用的改动（the shortest working diff wins）＋ ponytail 标注（the ponytail note）＋ 不能省的那几样（never cut input validation, error handling）：做法是计划挑的，这一步把它做到位——目标整体成真，只留让它成真的行，共用的函数改一处，故意的简化在旁边写明失效的条件和以后换成什么；做法在代码里走不通，就带着路径和行号停下来交回去。
- 第 3 步 ← 跑起来读真实输出（verify by running and reading actual output）：验证是终端里那几行字，而不是对命令会打印什么的推断。
- 第 4 步 ← 先定从哪一环开始不对（root cause first）＋ 两败即停（two strikes）：先指出结果从链条的哪一环开始不对，同一条验证命令失败两次就把两次原始输出和试过什么一起交回去。
